# 패키지 경계 검토

PR #177의 분리는 공통 UI에서 플랫폼 구현을 선택하던 문제를 줄였습니다. 다만 계약 패키지 안의 기본 정책과 실행 코드까지 모두 분리된 것은 아닙니다. 다음은 후속 변경 제안이며, 이번 충돌 해결에서 패키지 이름이나 공개 API를 추가로 바꾸지는 않았습니다.

## 우선 정리할 경계

| 현재 위치                         | 남은 결합                                                                                 | 권장 방향                                                                                                                         |
| --------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `agent-contract/src/index.ts`     | `AgentService`와 함께 기본 루프의 축약·도구 반복·병렬 실행 설정을 정의합니다.             | 서비스 계약과 도구 계약을 구분하고, 기본 알고리즘 설정은 에이전트 구현이 소유하게 합니다.                                         |
| `chat/src`                        | 대화 데이터 외에 공급자 목록, 스킬 저장·파일 로딩, 날씨·차트 도구 실행이 함께 있습니다.   | 대화 모델·변환·검증은 `chat`에 남기고, 설정·스킬 관리와 도구 실행을 밖으로 옮깁니다.                                              |
| `chat/src/platform.ts`            | UI 플랫폼 계약이 Cordis, 기본 에이전트 설정, MCP 클라이언트 패키지의 타입을 참조합니다.   | 화면이 사용하는 기능 계약과 Cordis 조립 계약을 분리합니다. MCP 설정 타입도 클라이언트 구현과 독립시킵니다.                        |
| `plugin-chat-browser/src/mcp.ts`  | 브라우저 연결 관리자가 네이티브 명령과 보안 저장소 저장 방식도 선택합니다.                | MCP 연결 관리에는 설정 저장 인터페이스를 주입하고, 브라우저 저장소와 네이티브 저장소 선택은 각각의 플랫폼이 담당하게 합니다.      |
| `agent-runtime-node/src/index.ts` | 환경 변수 해석, 기본 공급자 선택, MCP 연결, Agent Plugins 수명 관리가 한 파일에 있습니다. | 우선 `runtime`, `default-composition`, `mcp-tools` 모듈로 나눕니다. 독립 소비자가 생기기 전에는 패키지를 더 만들 필요가 없습니다. |

`chat → mcp → @modelcontextprotocol/client`는 현재 매니페스트 의존성입니다. `ChatPlatform`의 참조는 타입 전용이므로 이것만으로 SDK가 화면 번들에 포함된다고 판단할 수는 없습니다. 다만 설치와 빌드 의존성은 남습니다.

`tools/workspace-boundaries/check.mjs`는 특정 패키지 이름과 직접 참조를 검사합니다. `mcp`처럼 구현을 포함하면서 `plugin-`으로 시작하지 않는 패키지나, `chat` 내부의 구현 코드는 현재 규칙만으로 구분할 수 없습니다. 패키지 역할에 따른 허용 의존성도 검사하는 편이 낫습니다.

## 에이전트 계약의 범위

`AgentService.run()`은 교체 가능한 서비스 계약으로 유지할 가치가 있습니다. 반면 `maxToolRounds`, `parallelTools`, 축약 임계값은 현재 기본 실행 루프의 정책입니다. 다른 에이전트가 같은 설정 모델을 구현하도록 요구할 필요는 없습니다. 호스트가 전달하는 공통 실행 정보와 기본 에이전트의 설정을 분리하고, 앱의 조립 함수가 둘을 연결하도록 권장합니다.

`ExecutableTool`은 MCP와 파일·셸 도구에서도 사용합니다. 에이전트 구현에 종속시키지 않는 현재 방향은 맞습니다. 독립적인 도구 소비자가 이미 여러 개이므로, 후속 변경에서 별도의 `tools` 계약으로 옮기는 근거도 충분합니다.

이름은 기존 `fs`·`shell`·`transcription` 규칙에 맞춰 `agent`를 계약, `plugin-agent-default`를 기본 구현으로 두면 역할이 명확합니다. 다만 이름 변경만으로 결합이 사라지지는 않으며, 기존 `Agent` 상속과 import 경로의 이전 비용도 있습니다. 먼저 위 설정 경계를 정한 뒤 이름을 함께 바꾸는 편이 좋습니다.

## 플랫폼 패키지의 크기

`plugin-chat-local`과 `plugin-chat-remote`는 저장·실행 방식과 수명이 달라 독립적인 교체 단위입니다. 이 경계는 유지하는 편이 좋습니다. 두 구현은 Cordis 플러그인 자체라기보다 채팅 어댑터이므로 `chat-local`, `chat-remote` 같은 이름도 검토할 수 있습니다.

반면 브라우저 LLM·모델 목록·전사 어댑터는 현재 플랫폼에서 함께 선택하는 기본 구성입니다. 작은 어댑터마다 패키지를 늘리기보다 `platform-browser` 아래의 공개 하위 경로로 묶는 방안이 있습니다. 데스크톱 IPC와 보안 저장소는 `platform-desktop`이 소유하게 합니다. 실제 공급자 플러그인과 로컬·원격 채팅 구현은 계속 독립적으로 교체할 수 있어야 합니다.

권장 순서는 `chat` 내부의 실행 코드 분리, MCP 설정 저장소 주입, 에이전트 공통 계약과 기본 설정 분리, 패키지 이름·통합 정리입니다. 파일 수보다 교체 이유와 의존성 방향을 기준으로 진행합니다.
