# 도메인 문서

이 문서는 엔지니어링 스킬이 코드베이스를 탐색할 때 도메인 문서를 활용하는 방법을 정한다.

## 탐색 전, 다음을 읽는다

- 저장소 루트에 `CONTEXT-MAP.md`가 있으면 그 파일을 읽는다. 이 파일은 컨텍스트마다 하나의 `CONTEXT.md`를 가리킨다. 주제를 다루는 각 파일을 읽는다.
- 루트에 `CONTEXT-MAP.md`가 없으면 저장소 루트의 `CONTEXT.md`를 읽는다.
- **`docs/adr/`**: 곧 작업할 영역을 다루는 아키텍처 결정 기록(ADR)을 읽는다. 다중 컨텍스트 저장소에서는 컨텍스트별 결정을 위해 `src/<context>/docs/adr/`도 확인한다.

이 파일들 중 하나라도 없으면 파일이 없다고 알리지 않고 작업을 계속한다. 미리 만들라고 제안하지 않는다. 용어나 결정이 실제로 확정될 때마다 `/vibe-plan`이나 `/vibe-refactor`는 `/vibe-modeling` 스킬을 로드해 그 지침을 따른 뒤 `CONTEXT.md`나 ADR을 만든다.

## 파일 구조

컨텍스트가 하나인 저장소는 다음 구조를 쓴다:

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

루트에 `CONTEXT-MAP.md`가 있으면 다중 컨텍스트 저장소다. 구조는 다음과 같다:

```
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← 시스템 전체 결정
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← 컨텍스트별 결정
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## 용어집 어휘 사용

출력에서 도메인 개념의 이름을 정할 때 `CONTEXT.md`에 정의된 용어를 그대로 사용한다. 이슈 제목, 리팩터 제안, 가설, 테스트 이름이 그 예다. 용어집이 명시적으로 피하는 동의어를 쓰지 않는다.

용어가 한국어, 영어 또는 혼합 표기여도 번역하거나 음역하거나 풀어 쓰거나 일반화하거나 중립화하거나 동의어로 바꾸지 않는다. 주제를 다루는 ADR이나 `docs/agents/`가 용어를 더 좁게 정했다면 그 표기도 같은 방식으로 보호한다.

필요한 개념이 용어집에 없으면 두 가능성을 확인한다. 프로젝트에서 쓰지 않는 말을 지어냈다면 표현을 다시 검토한다. 용어집에 실제로 빠진 개념이라면 `vibe-modeling` 스킬을 로드해 지침에 따라 그 용어를 `CONTEXT.md`에 기록한다.

## ADR 충돌 표시

출력이 기존 ADR과 모순되면 조용히 덮어쓰지 말고 명시적으로 드러낸다:

> _ADR-0007(이벤트 소스 주문)과 모순된다. 그래도 다시 논의할 가치가 있는 이유는 {이유}이다._
